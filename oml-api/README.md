# oml-api 稳定性声明与弃用策略

本文件是 `oml-api` 对 mod 作者的**兼容性契约**：哪些签名可以长期依赖、哪些允许随游戏版本演进、
破坏性变更如何提前告知。版本号的唯一真源是仓库根 `gradle.properties` 的 `oml_version`（构建时
戳进 `oml-core.properties`，运行期横幅与发布坐标都读它）。

## 三层稳定性

| 层 | 内容 | 承诺 |
|----|------|------|
| **契约层** | `@Mod` 入口、`OMLModInitializer` / `ModContext`、`Events` 全部事件、`ContentRegistry` 声明 DSL、注入 DSL（`@RuleSource` / `RuleSetProvider` / 锚点与改写原语） | 语义与签名按语义化版本向后兼容；破坏性变更必须先以弃用形式存在一个次版本 |
| **已提供、仍在沉淀** | 命令 DSL（`command`）、配置（`config`）、网络（`network`）、按键 / HUD / 创造标签（`client`）、`ModContext.config` | 0.x 阶段允许随版本调整（调整记录进发布说明与 `docs/forensics.md`）；1.0 起升入契约层 |
| **逃生舱（无稳定性承诺）** | 一切 `platform` 属性暴露的原生对象、`OMLCore` 的反射旁路（`gameClassLoader` / `serverInstance`） | 跟随游戏版本自由变动，任何版本都可能破坏——这是它们存在的目的：让 mod 作者在不等 OML 的情况下自救 |

判断一个签名属于哪一层：它若把游戏类型藏在了 OML 自己的抽象后面，就是契约层；它若把游戏对象
原样交给你，就是逃生舱。

## 版本号策略

- `0.x.y-SNAPSHOT`（当前）：主线开发版。`x` 变更代表一次允许破坏契约层的演进，破坏点逐条写入
  发布说明；`y` 变更只携带修复与新增。
- `1.0.0` 起：契约层冻结。破坏契约层的变更为**大版本**事件（`2.0.0`），旧签名经 `@Deprecated`
  （附替换指引）保留到下一个大版本；弃用起在启动日志中以 WARN 提示一次。
- "仍在沉淀"层在 1.0 之前不承诺兼容；进入 1.0 的内容会在发布说明中逐条宣布升层。

## 弃用的执行方式

- 代码内：`@Deprecated`（附 `ReplaceWith` 与原因），不加 `error` 级别的运行期拦截——mod 的
  运行不该被弃用打断。
- 文档内：本文件的变更记录 + 发布说明逐条列出；面向 mod 作者的站点文档同步更新。
- 仓库纪律：`oml-api` 的破坏性变更与弃用必须独立成提交（commit 信息里写明约束与迁移方式），
  不与功能修改混排。
